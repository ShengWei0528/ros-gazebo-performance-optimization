# 研究方法與結果

*本文整理自元智大學畢業專題（2025）的每週進度報告與總結報告。English version: [write-up.md](write-up.md)。*

## 1. 問題

ROS 搭配 Gazebo 是常見的機器人開發與模擬平台，但模擬需要大量運算與繪圖資源。在有限的硬體環境（本研究為 Windows + WSL2）下，模擬經常無法即時運行：**即時因子（Real-Time Factor, RTF）** 低於 1.0，CPU 與記憶體使用率偏高，拖慢每一次實驗。

**目標：** 找出 TurtleBot3 Gazebo 模擬中 CPU 時間花在哪裡，並依「圖形 → 感測器 → ROS 通訊 → 作業系統排程」逐層排除瓶頸，讓模擬達到 RTF ≥ 1.0 並保留運算餘裕。

## 2. 實驗環境

| 項目 | 設定（依報告記載） |
|---|---|
| 主機 | Windows 10 + WSL2、Ubuntu 20.04 LTS、4 個邏輯處理器 |
| 中介軟體 | ROS 1 Noetic |
| 模擬器 | Gazebo 11 |
| 機器人 | TurtleBot3 Waffle Pi（第 1–2 週）；TurtleBot3 Burger + LDS-01 雷射（2.5 Hz，第 4–6 週）；第 5 週另加攝影機與 9 軸 IMU |
| 場景 | `turtlebot3_world`（第 1–2 週）；含障礙物的簡易室內房間（第 6 週） |
| 指標 | RTF（`gz stats`）、CPU 與記憶體（`htop`/`top`）、topic 頻率與延遲（`rostopic hz`） |

CPU 百分比採 `htop` 慣例：100 % = 一顆核心滿載，4 核心系統最高可到 400 %。

## 3. 各階段方法與結果

### 第 1 週：環境建置與瓶頸分析

- 以 Waffle Pi 模型與 Gazebo GUI 啟動 `turtlebot3_world`。
- `htop` 觀察：`gzserver`（物理與感測器模擬）約 50 % CPU，`gzclient`（圖形渲染）約 35 %，ROS 核心程序（`rosout`、`roslaunch`）合計低於 25 %。**結論：ROS 通訊不是瓶頸，物理運算與渲染才是。**
- 下週方向：關閉陰影、移除多餘光源、測試無 GUI 模式。

> 第 1 週報告本身的初次量測為 RTF 1.00、CPU 約 110 %、記憶體約 1066 MB；之後的總結報告則以 RTF 0.40、CPU 約 150 %、1.5 GB 作為預設 GUI 的「優化前」基準。兩者皆依原紀錄保留，因無原始紀錄檔可供比對。

### 第 2 週：圖形渲染設定與無 GUI 模式

1. 複製官方 world 檔並修改副本（見 [`configs/optimized_world_snippet.sdf`](../configs/optimized_world_snippet.sdf) 與截圖 `figures/week2_optimized_world_file.png`）：
   - `<scene>`：`shadows=false`、`grid=false`、`origin_visual=false`
   - `sun` 光源：`cast_shadows=false`
   - 移除重複的設定
2. 分別以 GUI 模式與無 GUI 模式（`gui:=false`，只執行 `gzserver`）執行優化後的場景。

| 模式 | RTF | CPU | 記憶體 |
|---|---|---|---|
| 預設 GUI（第 1 週基準） | 0.40 | ≈150 % | 1.5 GB |
| 優化場景＋GUI | 1.00 | ≈94 %（gzserver 48 % + gzclient 46 %） | 1.02 GB |
| 優化場景＋無 GUI | 1.00 | ≈46 % | 387 MB |

改為無 GUI 後，CPU 少了約 48 個百分點（相對優化 GUI 下降 51 %），記憶體減少約 630 MB，RTF 維持 1.00。**報告建議：** 不需要人機互動的模擬（自主導航、強化學習訓練、多機器人模擬）一律使用 `gui:=false`。

### 第 3 週：感測器參數

以批次腳本下修 LiDAR 與攝影機的解析度與更新頻率。依六週總結記載，CPU 再降約 33 %；此週沒有獨立報告或數據表。

### 第 4 週：LiDAR 訂閱節點改寫為 Nodelet

Nodelet 讓多個節點以 plugin 形式在同一個進程（nodelet manager）中執行，訊息以指標傳遞，省去跨進程的序列化與複製。

流程：建立 Nodelet 套件，撰寫 Nodelet 類別與功能等價的一般節點 → 撰寫 plugin 描述檔 → 修改 `CMakeLists.txt`、`package.xml` 註冊 → `catkin_make` → 撰寫啟動 nodelet manager 並載入 LiDAR Nodelet 的 launch 檔。量測前先確認兩種版本都能持續印出 `/scan` 的最小距離。

| 模式 | RTF | CPU | `/scan` 延遲 |
|---|---|---|---|
| 一般節點 | 1.00 | 42 % | 3.2 ms |
| Nodelet | 1.02 | 38 % | 1.5 ms |

省去跨進程複製後，延遲約減半（−53 %）。

### 第 5 週：所有感測器改為 Nodelet

LiDAR、攝影機與 IMU 濾波節點全部改寫，並由同一個 nodelet manager 載入。

| 指標 | 僅 LiDAR Nodelet | 全部感測器 Nodelet | 變化 |
|---|---|---|---|
| RTF | 1.02 | 1.00 | −0.02 |
| CPU | 38 % | 30 % | −8 個百分點 |
| 記憶體 | 1.30 GB | 1.20 GB | −0.10 GB |
| `/scan` 延遲 | 1.5 ms | 1.2 ms | −20 % |
| `/camera` 延遲 | 5.5 ms | 2.8 ms | −49 % |
| `/imu` 延遲 | 1.8 ms | 1.0 ms | −44 % |

攝影機與 IMU 的延遲降幅接近一半，報告歸因於零拷貝傳輸。整合後節點較多、負載略增，RTF 小降但仍維持即時。

### 第 6 週：高負載下的作業系統排程

為了讓排程效果更明顯，在無 GUI 模擬（TurtleBot3 Burger 在房間中巡航掃描）之外，另外啟動一個**以 OpenBLAS 持續做矩陣運算的高負載 ROS 節點**，模擬 SLAM 或強化學習等重運算。比較五種策略：

1. **預設**：Linux CFS 排程，不綁核心。
2. **即時優先權**：`chrt -f -p 99 <gzserver_PID>`（SCHED_FIFO），讓物理迴圈不被搶占。
3. **CPU 親和性**：以 `taskset` 將 `gzserver` 綁在 CPU0，高負載節點在 CPU1–2，其他 ROS 節點在 CPU3。
4. **優先權＋親和性**並用。
5. **優先權＋親和性＋`OPENBLAS_NUM_THREADS=1`**，避免 OpenBLAS 依核心數開滿執行緒。

| 策略 | RTF | 總 CPU | 估計 `/scan` 延遲 | 記憶體 |
|---|---|---|---|---|
| 預設（CFS） | 0.68 | 380 % | 8.5 ms | 500 MB |
| 僅即時優先權 | 0.85 | 370 % | 5.0 ms | 500 MB |
| 僅 CPU 親和性 | 0.88 | 355 % | 4.1 ms | 498 MB |
| 優先權＋親和性 | 0.95 | 360 % | 3.2 ms | 498 MB |
| ＋OpenBLAS 單執行緒 | **1.03** | **180 %** | **2.5 ms** | 480 MB |

第 6 週報告提供這些數值時沒有附上原始紀錄或量測截圖，此處依報告原文呈現，未再驗證。

報告中的觀察：

- 優先權與親和性各自有效，且效果可疊加（0.68 → 0.95）：優先權讓 `gzserver` 不被打斷，親和性讓它獨佔一顆核心。以 RTF 來看，大部分的提升來自這兩步。
- 限制 OpenBLAS 為單執行緒帶來最大的 CPU 降幅，也是讓 RTF 超過 1.0 的那一步（0.95 → 1.03）。在 CPU 已接近飽和時，多出來的 BLAS 執行緒主要只帶來競爭與同步開銷；限制後總 CPU 約減半（≈360 % → 180 %），而報告指出計算任務本身的結果不受影響。
- 預設情況下 `/scan` 實際發布頻率低於標稱的 2.5 Hz（約 1.7 Hz），調整後恢復到 2.5 Hz。
- 記憶體幾乎不變（480–500 MB），效能提升來自排程改善，而非以記憶體換取速度。
- 注意：SCHED_FIFO 優先權 99 需要管理者權限，設定不當可能讓其他程序得不到 CPU；報告認為在 WSL2 單一模擬任務下風險可控。

## 4. 整體進展（ROS 1）

| 階段 | RTF | CPU | 記憶體 | 主要措施 |
|---|---|---|---|---|
| 優化前 | 0.40 | ≈150 % | 1.50 GB | 無 |
| 圖形渲染優化 | 1.00 | ≈46 % | 387 MB | 關閉陰影、移除光源、無 GUI |
| Nodelet 架構 | 1.02 | ≈38 % | ≈380 MB | LiDAR Nodelet 化 |
| 系統資源調度 | 1.02 | ≈38 % | ≈380 MB | CPU 親和性、即時排程 |

此表為第一次總結報告（2025 年 5 月）的表一。與其起點相比：RTF 0.40 → 1.02（+155 %），CPU ≈150 % → ≈38 %（−75 %），記憶體 1.5 GB → ≈380 MB（−75 %），雷射延遲 3.2 ms → 1.5 ms（−53 %）。圖形渲染優化帶來最大幅度的提升，Nodelet 與排程優化主要改善延遲與穩定性。

> **各報告在兩處不一致。**（1）起點：第 1 週報告量到預設 GUI 設定為 RTF 1.00、CPU 約 110 %、約 1.07 GB，而本表（以及第 2 週的跨週比較表）記為 0.40、約 150 %、1.5 GB。（2）Nodelet 化後的記憶體：本表的 Nodelet 與排程階段約 380 MB，但第 5 週報告同一階段記為 1.30 GB → 1.20 GB，六週總結的最終狀態也是 1.2 GB。由於沒有原始紀錄可供比對，記憶體數字尤其需要保留看待。

## 5. 調查過的其他優化手法

2025 年 5 月的報告另外整理了其他可行的優化方式，以下僅作為檢查清單，**本專題並未逐項量測**：

- *ROS 層：* Nodelet / 組合式節點、訂閱端啟用 `TCP_NODELAY`、減少 relay node、控制話題頻率與資料大小、時間戳同步。
- *Gazebo 層：* 精簡碰撞幾何與模型細節、調整 `max_step_size` / `real_time_update_rate`、關閉不必要的感測器、無 GUI 模式、避免 blocking 的 plugin callback、減少 link/joint、使用 GPU 感測器（`gpu_ray`）、CPU 綁定、關閉 skybox / 霧效 / 陰影、精簡 world。

## 6. 限制與後續方向（依報告）

- 物理運算仍是主要負載：Gazebo 物理引擎約佔單核心 50 %；可考慮降低更新率或改用 Ignition Gazebo。
- 目前只驗證單一機器人，下一步規劃 3 台 TurtleBot 同時模擬。
- 攝影機與影像處理節點仍需進一步優化。
- 排程方面可再嘗試 `isolcpus`、cgroups 與即時核心（Realtime Kernel）。
- 將所有優化步驟整理成自動化腳本，做到一鍵重現。
- 量測品質：各項數字為 `htop` / `gz stats` 的單次讀值，各週條件不同，部分報告之間的數字也不一致（見第 4 節）；若能重複量測並保存原始資料，比較會更具統計意義。
